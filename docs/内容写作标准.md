# 内容写作标准

> 这份文档是给"继续写/改内容"的人和 agent 用的。
> 起因：第一版内容偏薄——术语只有一句判据、单元之间没有承接说明，
> 读者拿到的是"一堆正确的碎片"，而不是一条线。

---

## 一、每个单元必须回答的四个问题

站内的单元不是百科条目，是**学习路径上的一站**。所以每个单元必须能回答：

| 问题 | 写在哪 | 不写会怎样 |
|---|---|---|
| **我为什么现在学这个？** | `flow.why` | 读者不知道它和前后有什么关系，像在背孤立的规则 |
| **它承接了什么？** | `flow.from` | 不知道哪些前置知识是必需的 |
| **学完去哪？** | `flow.to` | 学完就断了，不知道下一步为什么是它 |
| **学完我能做什么？** | `goal` | 无法自检，也不知道练到什么程度算够 |

### 写法

```js
SITE.unit({
  id: 'A2', code: 'A2', track: 'harmony', order: 2, minutes: 200,
  title: '终止式全谱系',
  goal: '……（要具体可检验，不要写"了解""掌握"）',

  flow: {
    from: 'A1 的数字低音与转位',
    why: '你刚学会看一个和弦是什么。<b>但曲式分析的最小单位不是和弦，是乐句的结束</b>——' +
         '而乐句的结束靠终止式认定。不先建立终止式的判据，后面 C 模块的曲式分析无从下手。',
    to: 'A 模块到此结束。接着进 B 模块学对位——你会发现<b>终止式在对位里是一条硬规则</b>，' +
        '而这里的判据就是那条规则的来源。'
  },
  // ...
});
```

`flow.from` / `flow.to` 会渲染在单元页顶部的位置条和底部的方框里；
`flow.why` 渲染在目标条下面。

## 二、术语表：一句判据不够，要写透

`terms` 每行四个字段：

```js
['中文名', 'english', '一句判据', '展开讲解（可选，但强烈建议写）']
```

第四个字段渲染成单元格内的展开段落。**它要回答的是：这条判据为什么成立、容易和什么混淆、一个具体例子。**

### 反例（第一版的写法，太薄）

```js
['完全协和', 'perfect consonance', '纯一度、纯五度、纯八度。稳定但空洞，不可连续同向']
```

问题：读者知道有哪几个音程，但不知道**为什么**这四个字这么重要，
也不知道"不可连续同向"背后是什么后果。

### 正例

```js
['完全协和', 'perfect consonance',
 '纯一度、纯五度、纯八度（含复音程）。稳定但空洞，不能连续同向使用。',
 '<b>为什么"空洞"是缺点？</b>完全协和的音响里，两个音的频率比是最简单的整数比' +
 '（八度 2:1、五度 3:2），听觉上融成一个整体，听不出是两个独立的声部。' +
 '复调的目的恰恰是让每个声部都被听见，所以完全协和只能是"骨架"——' +
 '用来定调性、定结构、作终止，不能当主要材料。<br>' +
 '<b>容易混淆：</b>不完全协和（三度、六度）听起来"更满"，' +
 '有人误以为它们比五度八度"更协和"。协和度不是一个从坏到好的刻度，' +
 '而是<b>两种功能</b>：完全协和=稳定但融合，不完全协和=丰满且声部独立。' +
 '对位写作的主体是后者。<br>' +
 '<b>例子：</b>纯五度连续同向两次以上就是平行五度，' +
 '正因为听觉上两次都"融成一体"，声部数会从两个变成一个。']
```

### 什么时候可以不写第四项

只写一句判据是允许的，但只在这两种情形：
- 纯查表性质的条目（如某个数字低音的写法），本身没有"为什么"
- 该术语在紧邻的正文里已经讲透了

**其余情况都补上。** 判断标准很简单：**只写判据的话，读者能不能靠它自己判断一个新情况？**
不能就说明没讲透。

## 三、正文（`prose`）的写法

### 每个 `prose` 区块只讲一件事

标题就是那件事的结论。**不要用"介绍""概述""说明"这类空标题。**

反例标题：`'基本概念'`、`'几个要点'`、`'补充说明'`
正例标题：`'为什么平行五八度这么严重'`、`'这一类的全部新知识，只有一句话'`、`'怎么判断一个音凭什么在这里'`

### 讲清一个概念的四步

1. **它是什么**（一句话）
2. **判据是什么**（可操作的检查步骤）
3. **为什么这样**（背后的听觉或结构理由）
4. **容易错在哪**（具体的错误形态 + 为什么会犯）

第 3、4 步是第一版最缺的。**只写 1、2 就成了手册，不是教材。**

### 判据必须可操作

反例：`'注意声部进行的合理性'`
正例：`'两声部同向进行、且同时跳到完全协和音程 → 隐伏五八度。若上方声部为级进，多数体系允许。'`

判断标准：**读者能不能照着它逐音核对？** 不能就重写。

## 四、单元之间的知识依赖要显式写出来

除了 `flow`，正文里也要点明依赖。例如 B4（挂留）开头应该写：

> 第四类用到三个东西，全在前面学过：① B2 的"弱拍不协和必须级进处理"；
> ② B1 的"完全协和不能连续"；③ A2 的终止式判据——因为挂留最常见的用法就是终止式接近。
> **如果这三条里有哪条想不起来，先回去重看，否则这一章会很吃力。**

这种"回头指路"的话成本极低，但对自学的人是决定性的。

## 五、诚实性要求（不能省）

- 有分歧的地方要写明**分歧在哪、会导致什么不同结论**
- 不确定的要标出来，不要用笃定的语气糊过去
- 引用真实文献时只给"作品 + 小节范围 + 任务 + 链接"，**不要编造谱面细节**
- 自己定的私有规范（如 E4 的字段表）要声明"这是本站自定，不对应任何标准"

### 5.1 同一概念在两套体系里口径不同时 —— 并列写，不要二选一

本站**同时**使用两套体系：**Caplin 管曲式分析，DCML 管和声标注**。
同一个术语在两套里的判据可能不同，此时**不许挑一个当作唯一真理**，必须：

1. **第一句判据标明口径** —— 写成「（Caplin 口径）……」或「（DCML 口径）……」
2. **并列写出另一套的口径**
3. **指出在哪种具体情况下两者结论相反** —— 这是最有价值的一句话
4. **给出使用规则** —— 什么场合用哪一套

#### 已确认的实例（写内容时不要再踩）

| 概念 | Caplin 口径 | DCML 官方口径 | 冲突情形 |
|---|---|---|---|
| **PAC** | V→I，**两个和弦均原位**，最高声部落主音 | **只要求**低音与最高声部同时落在 ^1，**不提原位** | `V6 → I` 且外声部都落 ^1：Caplin 判 IAC，DCML 判 PAC |

**使用规则**：做曲式分析用 Caplin；做 DCML 标注**以官方表为准**——否则标签过不了同行评审。

#### 另一类：不是冲突，是"两道工序"

有时两组"条件"看起来不一致，其实在回答**不同问题**，这时要说清分工而不是合并：

| | 回答的问题 | 例子 |
|---|---|---|
| **类型判据** | 它是哪一种？（PAC 还是 IAC） | Caplin 三条件里关于和声进行与原位的那两条 |
| **结构认定判据** | 它算不算数？（是不是一个 formal cadence） | Caplin 要求终止主和弦落在有重音的位置 |

A2 讲类型，C3 讲结构认定。**两者不冲突**，正文里要明说这一点，不要让读者以为哪里写错了。

## 六、区块字段：少写一个字段会把整个单元打崩

内容不只是文字，它是**喂给渲染器的数据**。渲染是同步的，一个区块少写必需字段，
`pageUnit` 就会在那一块抛异常 —— 以前的表现是整个单元白屏，连已经写好的部分也看不到。

`site.js` 现在给每个区块包了 try/catch，坏掉的那一块会渲染成一张说明卡片，
**其余内容照常显示**。但那只是"别白屏"，不是"这样写没问题"。
所以这几条由 `tools/check-content.js` 直接拦下（硬性项，不达标就退出码 1）：

| 区块 | 必需 | 说明 |
|---|---|---|
| `drill` (`quiz`) | `options`，且至少一个 `ok: true` | 没有正确选项的题永远答不对 |
| `drill` (`spot`) | `options`（至少一个带 `rule`）、`cf`、`cp` | 引擎直接对 `cf` 调 `.replace()`，缺了就是崩 |
| `drill` (`label`) | `answers` | 没有参考答案，答对也不判对 |
| `terms` | `items` | |
| `checklist` | `items` | |
| `repertoire` | `items` | |
| `listen` | `notes` | 没有可播的音 |
| `note` / `html` | `html` | |
| `score` | `svg` | 没有谱面就只剩占位提示 |

另外两条与文件有关（也在 `check-content.js` 里）：

- `score` 的 `svg` / `mp3` / `mscz` **文件必须真的存在** —— 渲染器对缺失文件都有兜底
  （占位提示、报错提示），所以"文件没了"不会报错，只会静默变丑。
- 谱面**不要再内联打包**回 `assets/scores/scores.js`。那个文件已按架构决定删除：
  它让首屏多下近 1 MB 的重复数据，而 http(s) 下谱面本来就按需读 `assets/scores/*.svg`。
  `check-content.js` 与 `check-musicxml.js` 都会在它重新出现时失败。

三条**提示级**（不拦，只是提醒这一块少了什么）：
`label` 既没有 `notes` 也没有 `context`、`score` 没有 `mp3`、`score` 没有 `mscz`。

## 七、自查清单

写完一个单元，逐条过：

- [ ] `flow.from` / `flow.why` / `flow.to` 都写了，且 `why` 说清了"为什么是现在"
- [ ] `goal` 是可检验的（"能写出/能判断/能说出"，不是"了解/熟悉"）
- [ ] 每个 `terms` 条目要么有第四项展开，要么属于上面说的两种例外
- [ ] 每个 `prose` 的标题就是那件事的结论，没有"介绍/概述"这类空标题
- [ ] 关键概念都回答了"为什么这样"和"容易错在哪"
- [ ] 判据都能照着逐音核对
- [ ] 正文里点明了依赖的前置单元
- [ ] 分歧处标注了分歧
- [ ] `drill` 的讲解说的是"为什么这个选项不对"，不只是"正确答案是 X"
- [ ] `node tools\check-content.js` 通过（它按本标准逐条验收，包括第六节的字段契约）
